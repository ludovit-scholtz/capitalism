## Findings

### 1) MasterApi Auth Rate Limiting Still Misses Named-Operation and Batched Login/Register Requests

- **Severity:** Medium
- **Affected:** `projects/MasterApi/Security/AuthRateLimitMiddleware.cs`
- **Description:** `IsAuthOperation(GraphQlHttpRequest? request)` still trusts the HTTP `operationName` field before inspecting selected GraphQL root fields, and the middleware only deserializes a single JSON-object request body. A caller can supply a non-auth `operationName` while selecting the `login` or `register` mutation, or place those mutations inside a JSON-array batch envelope, and avoid the MasterApi per-IP auth limiter. The game API no longer has this gap because it parses selected root fields across all request items.
- **Impact:** Attackers can increase password-guessing and registration-abuse throughput against MasterApi beyond the intended throttling budget. Account-aware controls and default configuration still reduce exposure, but the first-line auth-abuse limiter is weaker than intended on the master surface.
- **OWASP:** API2 Broken Authentication, API4 Unrestricted Resource Consumption, API6 Unrestricted Access to Sensitive Business Flows.
- **Recommendation:** Port the game API's GraphQL root-field parsing and batch-item iteration into `projects/MasterApi/Security/AuthRateLimitMiddleware.cs`, or extract a shared helper used by both APIs. Add regression tests for named operations, JSON-array batches, and mixed auth/non-auth batch envelopes.
- **Status:** Open

### 2) MasterApi Custom GraphQL Request-Security Middleware Only Inspects Single JSON-Object Bodies

- **Severity:** Low
- **Affected:** `projects/MasterApi/Security/GraphQlRequestSecurityMiddleware.cs`
- **Description:** `TryExtractQuery()` reads only `RootElement.TryGetProperty("query", ...)` and therefore ignores JSON-array batched request bodies. HotChocolate's built-in depth and cost controls still reduce denial-of-service exposure, but the MasterApi's custom non-Development introspection rejection, normalized error contract, and warning telemetry are not applied per batch item.
- **Impact:** If GraphQL batching is enabled on MasterApi, a caller can avoid the custom rejection telemetry and the middleware's standardized pre-execution responses by wrapping requests in array envelopes. This is a hardening gap rather than a confirmed full bypass of the built-in GraphQL limits.
- **OWASP:** API4 Unrestricted Resource Consumption, API8 Security Misconfiguration, API9 Improper Inventory Management.
- **Recommendation:** Decide explicitly whether MasterApi supports GraphQL batching. If batching is not required, reject JSON-array envelopes early. If batching is supported, iterate through every request item and apply the same parse, introspection, depth, and complexity checks that the game API now performs.
- **Status:** Open

### 3) Game Frontend Still Persists Raw JWTs in `localStorage` After Cookie-Session Bootstrap

- **Severity:** Low
- **Affected:** `projects/frontend/src/stores/auth.ts`, `projects/frontend/src/lib/graphql.ts`
- **Description:** `applyStoredSession()` still writes `auth_token` and `auth_expires` into `localStorage` after login, register, and OIDC callback flows. The gameplay GraphQL client already uses cookie-backed `credentials: 'include'` and does not attach bearer `Authorization` headers for normal requests, so raw token persistence is now primarily a bootstrap artifact rather than an active gameplay transport requirement. The master frontend has already narrowed this pattern by persisting sentinel or metadata state while keeping the raw token in memory during session establishment.
- **Impact:** A successful XSS in the game frontend could still steal a live bearer token even though routine gameplay requests already use cookies. Token revocation and expiry reduce the blast radius, but the browser exposure is unnecessary and the current roadmap text overstates the hardening that is actually complete.
- **OWASP:** API2 Broken Authentication.
- **Recommendation:** Remove raw token writes from `projects/frontend/src/stores/auth.ts` and rehydrate gameplay sessions from the cookie session instead of `localStorage`. Add regression tests for login, OIDC callback, reload, and logout so the storage cleanup does not regress session bootstrap.
- **Status:** Open

## Recommendations

1. Align `projects/MasterApi` with the hardened game API path for GraphQL auth request classification and batch handling so MasterApi cannot be brute-forced through the older operation-name and single-body shortcuts.
2. Make batching support explicit on MasterApi: either reject array envelopes or inspect every batch item in `GraphQlRequestSecurityMiddleware` before execution.
3. Remove the remaining raw-token persistence from `projects/frontend/src/stores/auth.ts` and rely on cookie-session rehydration for gameplay sessions.
4. Keep stale-audit cleanup part of the security workflow: the lexicographically latest audit file becomes authoritative for the audit-board gate, so previously fixed findings should be revalidated before they are copied into new reports.
5. Maintain focused regression coverage for building-market floor enforcement, loan-currency settlement, and MasterApi auth throttling whenever these surfaces change.
