## Findings

### 1) DOMPurify ≤3.4.10 (Production Runtime — Both Frontends)

- **Severity:** Low (moderate per npm audit)
- **Affected:** `projects/frontend/package.json`, `projects/master-frontend/package.json` — `dompurify: "^3.4.2"`, installed 3.4.2
- **CVEs:** GHSA-x4vx-rjvf-j5p4, GHSA-76mc-f452-cxcm, GHSA-hpcv-96wg-7vj8, GHSA-r47g-fvhr-h676, GHSA-vxr8-fq34-vvx9, GHSA-gvmj-g25r-r7wr, GHSA-rp9w-3fw7-7cwq, GHSA-cmwh-pvxp-8882
- **Description:** DOMPurify 3.4.2 is below the 3.4.11 threshold required to clear all eight current advisories. The vulnerabilities affect: `IN_PLACE` mode (XSS via attacker-controlled `nodeName`, clobbered root element, shadow root in `<template>.content`, and cross-realm `instanceof` bypass); `setConfig()` hook-clone guard bypass; `DEFAULT_ALLOWED_TAGS`/`DEFAULT_ALLOWED_ATTR` pollution via hook mutation; `SAFE_FOR_TEMPLATES` bypass; and Trusted Types policy poisoning after `clearConfig()`.
- **Application exposure:** `projects/frontend/src/lib/htmlSanitizer.ts` and `projects/master-frontend/src/lib/htmlSanitizer.ts` call `DOMPurify.sanitize(html, config)` in standard (non-IN_PLACE) mode with explicit ALLOWED_TAGS, ALLOWED_ATTR, and without `setConfig()`, hooks, or Trusted Types. None of the eight vulnerable code paths are exercised. Exploitability against the running application is therefore **low** given current usage patterns.
- **Residual risk:** If a future developer adds `IN_PLACE`, `setConfig()`, or hooks, the outdated version becomes directly exploitable. The app also depends on DOMPurify as its primary XSS defense layer for news and support-ticket HTML, so a library vulnerability in that layer warrants prompt remediation.
- **Recommendation:** Run `npm audit fix` in both frontend directories to update DOMPurify to ≥3.4.11. Pin the lower bound in `package.json` if needed (e.g. `"dompurify": "^3.4.11"`). Re-run `npm audit --omit=dev` after upgrading to confirm zero production vulnerabilities.
- **Status:** Open

### 2) Vite 7.3.3 Dev Server — Windows Developer Workstation Risk

- **Severity:** Low (production builds are not affected; only developer machines running `npm run dev` on Windows)
- **Affected:** `projects/frontend/package.json`, `projects/master-frontend/package.json` — `vite: "^7.3.3"`, installed 7.3.3
- **CVEs:** GHSA-v6wh-96g9-6wx3 (launch-editor NTLMv2 hash disclosure via UNC path), GHSA-fx2h-pf6j-xcff (`server.fs.deny` bypass on Windows alternate paths)
- **Description:** Vite 7.3.3 is within the vulnerable range 7.0.0–7.3.3. GHSA-v6wh-96g9-6wx3: the dev server's launch-editor feature passes an unsanitized path argument to an external process on Windows; an attacker with network access to the dev server who can trick the developer into clicking a crafted error-overlay link can coerce a UNC path traversal that causes Windows to send NTLMv2 credentials to an attacker-controlled server. GHSA-fx2h-pf6j-xcff: the `server.fs.deny` rule can be bypassed on Windows via alternate-path representations (8.3 names, forward/back-slash mixing), potentially leaking files under the project root to local network peers of the dev server.
- **Production impact:** Vite is a `devDependency`; these issues only affect the `npm run dev` development server. Built artifacts and production containers are not affected.
- **Recommendation:** `npm audit fix` in both frontend directories will update Vite to ≥7.3.4. This is the same command that resolves the DOMPurify issue above. If `npm audit fix` does not automatically bump Vite (due to a minor constraint), update `"vite": "^7.3.4"` explicitly in both `package.json` files.
- **Status:** Open

## New Feature Security Review — Discord Bot (PR #568)

### Link-Code Generation

`DiscordLinkCode.Generate()` uses `RandomNumberGenerator.GetInt32()` (CSPRNG) over a 32-character alphabet of length 8 characters, giving approximately 40 bits of entropy. Codes are stored hashed against the player account, expire after a configurable lifetime, and are consumed on first successful verify (set to `null` along with the expiry). The lookup (`FirstOrDefaultAsync(candidate => candidate.DiscordLinkCode == normalizedCode)`) is indexed on `DiscordLinkCode` (max-length 16 in the model), so brute-force enumeration is gated by the 15-minute default window and the platform CSRF/rate-limit surface.

### Gold Token Deposit / Withdrawal

- `CreateWithdrawalRequest` checks `player.GoldTokenBalance < amount` before debiting; the balance is debited at request-creation time (not at admin processing), so double-debit by processing the same withdrawal twice is prevented by the `request.Status != "PENDING"` guard.
- `ProcessGoldTokenDepositRequest` credits the player's balance on admin processing. A concurrent double-process is blocked by EF Core's optimistic concurrency: `player.ConcurrencyToken` is configured via `.IsConcurrencyToken()` in `MasterDbContext.OnModelCreating` (`line 170`) and is rotated on every gold balance write. The second concurrent `SaveChangesAsync()` will throw `DbUpdateConcurrencyException` rather than silently double-crediting.

### Chat Bridge

- `ForwardInGameChatToDiscord` on MasterApi is undecorated with `[Authorize]` by design (server-to-server call). It is gated by the shared `RegistrationKey` (compared with `string.Equals(..., StringComparison.Ordinal)`) plus a per-shard `ServerKey` validated against the `GameServers` table. Content is trimmed to 500 characters before being relayed to Discord.
- `PostBridgedChatMessage` on the game API mirrors the same trust boundary. Content is further capped at `MaxChatMessageLength` and the author display name is resolved server-side from the authenticated player record, not from caller input.
- Discord → in-game relay (`OnMessageReceivedAsync`): resolves the player email from the linked `DiscordUserId` in the database before posting; anonymous or unlinked Discord users are silently dropped.

No exploitable vulnerabilities were found in the Discord integration.
