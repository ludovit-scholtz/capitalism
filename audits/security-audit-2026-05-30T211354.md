## Findings

### 1) Company-Merge Tax Settlement Can Be Evaded (Unchecked, Unclamped `TryDebit`)

- **Severity:** Medium
- **Affected:** `projects/Api/Types/Mutation.CompanyMerge.cs` (~line 91)
- **Description:** When a player merges a target company they control (≥90% combined ownership) into a destination company, the code settles the target's income tax with:
  ```csharp
  var taxAmount = decimal.Round(taxableIncome * taxRate, 2, MidpointRounding.AwayFromZero);
  CompanyBankingService.TryDebit(targetCompany.BankAccounts, taxAmount);
  db.LedgerEntries.Add(new LedgerEntry { ... Category = Tax, Amount = -taxAmount ... });
  ```
  `CompanyBankingService.TryDebit` is **all-or-nothing**: if the company's available balance is less than `taxAmount` it returns `false` and debits **nothing**. The return value is ignored here, and `taxAmount` is computed from the full taxable income without being clamped to the available balance. A ledger entry recording `-taxAmount` is then written regardless of whether any money actually left the company, and the merge proceeds to transfer all remaining cash and assets to the destination company.
- **Contrast with the canonical path:** The periodic engine `TaxPhase` (`projects/Api/Engine/Phases/TaxPhase.cs`) does this correctly: it computes `settledTax = Math.Min(bankBalance, incomeTaxDue)` and records the *actual* settled amount. The merge path diverges from this pattern.
- **Exploit / unfair advantage:** A player accumulates taxable income in an asset-rich, cash-poor company (cash spent on buildings/units, or simply held below the tax due), then merges it. Because `TryDebit` fails silently for the full amount, the merge-time tax is never collected, while honest players settling through the normal yearly `TaxPhase` always pay whatever cash they hold. This lets a player sidestep a money sink and retain a competitive cash/asset edge, and it corrupts the ledger with a tax expense that was never paid.
- **OWASP:** API1 Broken Object Level Authorization (business-logic integrity), API6 Unrestricted Access to Sensitive Business Flows.
- **Recommendation:** Mirror the `TaxPhase` pattern in `MergeCompany`: compute `settledTax = Math.Min(CompanyBankingService.GetTotalBalance(targetCompany.BankAccounts), taxAmount)`, debit (and assert success on) `settledTax`, and record `-settledTax` in the ledger. Optionally block the merge with a dedicated error code when liquid funds cannot cover the full tax, to prevent partial evasion. Add a regression test that merges a cash-poor, taxable-income-positive company and asserts the collected tax equals the available balance and the ledger reflects only what was paid.
- **Status:** Open

### 2) MasterApi Auth Rate Limiting Still Misses Named-Operation and Batched Login/Register Requests

- **Severity:** Medium
- **Affected:** `projects/MasterApi/Security/AuthRateLimitMiddleware.cs`
- **Description:** `IsAuthOperation(GraphQlHttpRequest?)` still trusts the HTTP `operationName` field first and only deserializes a single JSON-object request body. A caller can supply a non-auth `operationName` while selecting the `login`/`register` mutation, or wrap those mutations in a JSON-array batch envelope, and avoid the MasterApi per-IP auth limiter. The game API (`projects/Api/Security/AuthRateLimitMiddleware.cs`) no longer has this gap because it parses selected GraphQL root fields across all request items.
- **Impact:** Higher password-guessing and registration-abuse throughput than the limiter intends. Account-aware controls and default config reduce exposure, but the first-line auth-abuse limiter is weaker on the master surface.
- **OWASP:** API2 Broken Authentication, API4 Unrestricted Resource Consumption, API6 Unrestricted Access to Sensitive Business Flows.
- **Recommendation:** Port the game API's GraphQL root-field parsing and batch-item iteration into the MasterApi limiter (ideally via a shared helper used by both APIs). Add regression tests for named operations, JSON-array batches, and mixed auth/non-auth batch envelopes.
- **Status:** Open (carried over from 2026-05-16; not yet fixed in this revision)

### 3) MasterApi Custom GraphQL Request-Security Middleware Only Inspects Single JSON-Object Bodies

- **Severity:** Low
- **Affected:** `projects/MasterApi/Security/GraphQlRequestSecurityMiddleware.cs`
- **Description:** `TryExtractQuery()` reads only `RootElement.TryGetProperty("query", ...)` and therefore ignores JSON-array batched request bodies. HotChocolate's built-in depth/cost controls still apply, but the MasterApi's custom non-Development introspection rejection, normalized error contract, depth/complexity checks, and warning telemetry are not applied per batch item.
- **Impact:** If GraphQL batching is enabled on MasterApi, a caller can wrap requests in array envelopes to avoid the custom pre-execution checks and rejection telemetry. This is a hardening gap rather than a confirmed full bypass of the built-in limits.
- **OWASP:** API4 Unrestricted Resource Consumption, API8 Security Misconfiguration, API9 Improper Inventory Management.
- **Recommendation:** Decide explicitly whether MasterApi supports GraphQL batching. If not, reject JSON-array envelopes early. If batching is supported, iterate every request item and apply the same parse, introspection, depth, and complexity checks the game API performs.
- **Status:** Open (carried over from 2026-05-16)

### 4) Game Frontend Still Persists Raw JWTs in `localStorage` After Cookie-Session Bootstrap

- **Severity:** Low
- **Affected:** `projects/frontend/src/stores/auth.ts` (~lines 497-498), `projects/frontend/src/lib/graphql.ts`
- **Description:** `applyStoredSession()` still writes `auth_token` and `auth_expires` into `localStorage` after login, register, and OIDC callback flows. The gameplay GraphQL client already uses cookie-backed `credentials: 'include'` and does not attach bearer headers for normal requests, so raw token persistence is now primarily a bootstrap artifact. The master frontend has already narrowed this pattern.
- **Impact:** A successful XSS in the game frontend could still steal a live bearer token even though routine gameplay requests use cookies. Token revocation, short lifetimes, CSP, and DOMPurify reduce the blast radius, but the browser exposure is unnecessary.
- **OWASP:** API2 Broken Authentication.
- **Recommendation:** Remove raw token writes from `projects/frontend/src/stores/auth.ts` and rehydrate gameplay sessions from the cookie session. Add regression tests for login, OIDC callback, reload, and logout so the cleanup does not regress session bootstrap.
- **Status:** Open (carried over from 2026-05-16)

## Recommendations

1. **(New, prioritize)** Fix the `MergeCompany` tax settlement to clamp to available balance and record only the amount actually debited, mirroring `TaxPhase`. Add a regression test for the cash-poor merge-evasion scenario.
2. Align `projects/MasterApi/Security/AuthRateLimitMiddleware.cs` with the hardened game-API root-field parsing and batch handling, ideally via a shared helper, and add named-operation/batched-body regression tests.
3. Make GraphQL batching support explicit on MasterApi: either reject array envelopes early or inspect every batch item in `GraphQlRequestSecurityMiddleware`.
4. Remove the remaining raw-token persistence from `projects/frontend/src/stores/auth.ts` and rely on cookie-session rehydration.
5. Audit the remaining unchecked `CompanyBankingService.TryDebit`/`TryCredit` call sites in engine phases for similar "ignored failure + phantom ledger" patterns, and standardize on the `Math.Min(balance, due)` clamp-and-record convention used by `TaxPhase`.
