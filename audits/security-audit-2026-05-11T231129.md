## Findings

### 1) Legacy economy mutation responses still leak foreign-object state and exact balance detail
- **Severity:** Medium
- **Affected projects:** `projects/Api`
- **Affected surfaces:** `Mutation.BuildingMarket.cs`, `Mutation.Exchange.cs`, adjacent banking and trade flows.
- **Description:** Several economy-sensitive mutations still return distinct state-revealing codes such as `COMPANY_NOT_FOUND`, `BANK_ACCOUNT_NOT_FOUND`, `BANK_ACCOUNT_MISMATCH`, and `BUILDING_NOT_FOR_SALE`, and still disclose precise affordability or inventory detail such as `Available:` and `Required:` values. This is the same residual object-authorization and competitive-intelligence issue carried by the active roadmap item.
- **Evidence:** `MakeOfferOnBuilding` still emits `COMPANY_NOT_FOUND` and `Insufficient funds. Available: ...`. `BuyFromExchange` still emits `BANK_ACCOUNT_NOT_FOUND`, `BANK_ACCOUNT_MISMATCH`, `Insufficient unit capacity. Available: ...`, and `Insufficient funds. Required: ... available: ...`. `SellToExchange` still emits `BANK_ACCOUNT_NOT_FOUND`, `BANK_ACCOUNT_MISMATCH`, and `Insufficient inventory. Available: ...`.
- **Potential impact:** An authenticated competitor can probe whether rival companies, bank accounts, sale listings, or stocked inventories exist and infer how close another player is to a liquidity or inventory threshold.
- **Status:** Open

### 2) Password-authentication surfaces lack throttling or lockout controls and still disclose duplicate-account existence on registration
- **Severity:** Medium
- **Affected projects:** `projects/Api`, `projects/MasterApi`
- **Description:** Both APIs expose password `Register` and `Login` mutations without failed-attempt counters, temporary lockout, CAPTCHA step-up, or ASP.NET Core rate-limiter middleware. In addition, both registration flows still return explicit duplicate-email errors (`DUPLICATE_EMAIL` / "An account with this email already exists."), which turns the registration path into an account-enumeration oracle. OWASP Authentication Cheat Sheet recommends login throttling, account lockout or equivalent anti-automation controls, and generic account-state responses to reduce user enumeration and credential-stuffing risk.
- **Evidence:** `projects/Api/Types/Mutation.Auth.cs` and `projects/MasterApi/Types/Mutation.Auth.cs` perform direct password verification and update `LastLoginAtUtc` without any failed-attempt persistence or step-up flow. `projects/Api/Program.cs` and `projects/MasterApi/Program.cs` configure authentication and GraphQL middleware but do not register `AddRateLimiter` or `UseRateLimiter`.
- **Potential impact:** Attackers can test leaked credentials or spray weak passwords against known email addresses at scale, and can cheaply confirm whether a target email already has an account before attempting password attacks.
- **Status:** Open

## Recommendations
1. Finish the `NOT_FOUND_OR_NOT_OWNED` plus balance-redaction pass for building-market, exchange, and related banking mutations so unauthorized probes cannot infer object existence, listing state, or exact funds or inventory.
2. Add password-auth abuse controls across both APIs: account-aware failed-login tracking, temporary or exponential lockout, ASP.NET Core `AddRateLimiter` and `UseRateLimiter` policies on unauthenticated auth endpoints, and generic duplicate-account registration responses.
3. Review whether `@vercel/node` is still required in `projects/frontend`. If it is required, upgrade or replace the vulnerable toolchain; if it is not required, remove it from the dependency graph so the full npm audit is clean.
4. Keep the zero-production-advisory baseline for both frontends in CI, but add a periodic full `npm audit` review for the game frontend so build-tooling debt does not stay invisible behind `--omit=dev` scans.
5. When the auth hardening work lands, add focused abuse-path tests for lockout, rate-limiter rejection, and non-enumerating registration behavior so the mitigation does not silently regress.
