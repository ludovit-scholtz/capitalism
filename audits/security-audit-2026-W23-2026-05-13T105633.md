## Findings

### 1) GraphQL Auth Rate Limiting Can Be Bypassed With Named Operations

- **Severity:** Medium
- **Affected:** `projects/Api/Security/AuthRateLimitMiddleware.cs`, `projects/MasterApi/Security/AuthRateLimitMiddleware.cs`
- **Description:** The auth rate limiter first trusts the HTTP `operationName` field. If it is present and not literally `login` or `register`, the middleware does not inspect the selected GraphQL root field. A request can name the operation something unrelated while selecting `login` or `register`, causing the mutation to execute without the per-IP auth throttle. The same middleware deserializes only a single JSON-object body, so JSON-array batched request bodies are not evaluated by the limiter.
- **Impact:** Attackers can increase password-guessing and registration-abuse throughput beyond the intended 10 requests per IP per minute. Account-aware lockout still limits repeated attempts against one known email, but registration spam and distributed credential-stuffing attempts have a weaker first line of defense.
- **OWASP:** API2 Broken Authentication, API4 Unrestricted Resource Consumption.
- **Recommendation:** Parse the selected GraphQL operation and root fields before classifying auth operations. Inspect every item in JSON-array batched bodies or reject GraphQL batching explicitly. Add regression tests for named operations, batched bodies, and mixed batched requests.
- **Status:** Open

### 2) Client-Controlled `X-Forwarded-For` Can Rotate Rate-Limit Identities

- **Severity:** Medium
- **Affected:** `projects/Api/Security/AuthRateLimitMiddleware.cs`, `projects/MasterApi/Security/AuthRateLimitMiddleware.cs`
- **Description:** `GetClientIp()` accepts the first value of `X-Forwarded-For` without verifying that the request came through a trusted reverse proxy. Direct clients can spoof this header and rotate the cache key used for auth rate limiting.
- **Impact:** A direct attacker can bypass per-IP auth throttling by sending different forwarded IP values. This does not bypass account-level lockout, but it weakens protection for registration abuse, unknown-email spraying, and distributed login probes.
- **OWASP:** API2 Broken Authentication, API4 Unrestricted Resource Consumption.
- **Recommendation:** Trust forwarded headers only when the remote address is in a configured trusted proxy list, or rely on ASP.NET Core Forwarded Headers Middleware configured with `KnownProxies` / `KnownNetworks`. Add tests proving untrusted spoofed headers do not change the limiter identity.
- **Status:** Open

### 3) GraphQL Security Middleware Does Not Inspect Batched JSON Bodies

- **Severity:** Medium
- **Affected:** `projects/Api/Security/GraphQlRequestSecurityMiddleware.cs`, `projects/MasterApi/Security/GraphQlRequestSecurityMiddleware.cs`
- **Description:** `TryExtractQuery()` parses the HTTP body and reads `RootElement.TryGetProperty("query", ...)`. That covers normal JSON-object GraphQL requests, but not JSON-array batched request bodies. If the GraphQL server accepts batching, batched items can bypass the custom pre-execution introspection, depth, and complexity checks. HotChocolate's built-in depth/cost configuration still provides protection, but the custom warning logs and standardized responses are not guaranteed for batched items.
- **Impact:** Attackers may be able to avoid custom rejection logging and standardized `FORBIDDEN`, `MAX_DEPTH_EXCEEDED`, or `MAX_COMPLEXITY_EXCEEDED` responses by using batched request envelopes.
- **OWASP:** API4 Unrestricted Resource Consumption, API7 Server Side Request Forgery / unsafe server-side processing analog, API10 Unsafe Consumption of APIs.
- **Recommendation:** Either reject JSON-array GraphQL batching at the middleware boundary or iterate through every batch entry and apply the same query parse, introspection, depth, and complexity checks. Cover both APIs with regression tests.
- **Status:** Open

### 4) Duplicate Registration Still Returns a Machine-Readable Email-Existence Code

- **Severity:** Low
- **Affected:** `projects/Api/Types/Mutation.Auth.cs`, `projects/MasterApi/Types/Mutation.Auth.cs`
- **Description:** Duplicate registration now uses a neutral human-readable message, but the GraphQL extension code remains `DUPLICATE_EMAIL`. A scripted caller can distinguish existing accounts from new accounts when password registration is enabled.
- **Impact:** The issue can be used as an email enumeration oracle. The default `PasswordAuthEnabled=false` setting reduces exposure on OIDC-only deployments, but the behavior remains risky on deployments that enable password auth.
- **OWASP:** API2 Broken Authentication.
- **Recommendation:** Normalize the public error code, message shape, and timing for duplicate registration outcomes while recording duplicate attempts internally for monitoring.
- **Status:** Open

### 5) Game API Seed Admin Password Remains a Committed Default

- **Severity:** Low
- **Affected:** `projects/Api/appsettings.json`, `projects/Api/Configuration/SeedDataOptions.cs`, `projects/Api/Data/AppDbInitializer.cs`
- **Description:** The game API still defaults the seed admin password to `ChangeMe123!`, and the initializer always hashes that configured value for the seeded admin if the admin player is missing. `PasswordAuthEnabled=false` reduces immediate exposure, but enabling password auth without overriding `SeedData__AdminPassword` would create a known administrator credential.
- **Impact:** Misconfigured deployments can seed an admin account with a known password, which would be privilege-critical if password auth is enabled or later re-enabled.
- **OWASP:** A05 Security Misconfiguration, API2 Broken Authentication.
- **Recommendation:** Remove the committed password default or replace it with a placeholder that is blocked outside Development. Add a non-Development startup guard when `Auth:PasswordAuthEnabled=true` and the seed admin password is missing, default, or placeholder.
- **Status:** Open

### 6) Browser Bearer Tokens Are Stored in `localStorage`

- **Severity:** Low
- **Affected:** `projects/frontend/src/stores/auth.ts`, `projects/master-frontend/src/stores/auth.ts`, GraphQL clients in both frontends.
- **Description:** Both frontends persist bearer tokens in `localStorage`. The current CSP, DOMPurify sanitization, and HTML sink inventory lower the likelihood of XSS, and server-side JWT revocation lowers the blast radius after detection. Still, any successful XSS can read the token directly.
- **Impact:** A frontend XSS would allow account takeover until token expiry or revocation.
- **OWASP:** A03 Injection, API2 Broken Authentication.
- **Recommendation:** Evaluate HttpOnly SameSite cookie sessions or a backend-for-frontend token pattern. If bearer tokens must remain in browser storage, keep CSP strict, preserve sanitization on every rich-content sink, and keep session revocation coverage strong.
- **Status:** Open

## Recommendations

1. Harden auth rate limiting first: parse selected root fields, handle or reject batched GraphQL bodies, and stop trusting unconfigured forwarded headers.
2. Update both APIs' duplicate-registration behavior so public error codes cannot be used as an email-enumeration oracle.
3. Remove the game API seed admin password default or add a non-Development startup guard tied to `Auth:PasswordAuthEnabled`.
4. Decide whether GraphQL batching is supported. If yes, apply all custom security middleware checks per batch item; if no, reject array envelopes explicitly.
5. Evaluate a cookie-backed or backend-for-frontend auth session model to reduce token theft risk from any future XSS.
6. Keep generated inventories (`audits/graphql-surface-inventory.json`, `audits/frontend-sink-inventory.json`) in the security review loop whenever GraphQL operations or rich-content sinks change.

## Conclusion

The current revision has a substantially stronger security posture than the previous W22 audit: the formerly open TLS, session-revocation, frontend-header, and production-secret default findings are now implemented. The new audit did not find High or Critical issues, and dependency scans remain clean. The next security work should focus on GraphQL pre-execution edge cases, forwarded-header trust, duplicate-registration normalization, and removing the remaining seed admin credential default.
