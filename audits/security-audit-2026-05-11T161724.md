## Findings

### 1) Legacy economy mutation responses still leak foreign-object state and precise balance detail
- **Severity:** Medium
- **Affected project or surface:** `projects/Api/Types/Mutation.BuildingMarket.cs`, `projects/Api/Types/Mutation.Exchange.cs`, adjacent banking and trade flows.
- **Risk description:** The codebase has partially adopted `NOT_FOUND_OR_NOT_OWNED` semantics, but several economy-sensitive mutations still return distinct foreign-object or state-revealing outcomes such as `COMPANY_NOT_FOUND`, `OFFER_NOT_FOUND`, `BUILDING_NOT_FOR_SALE`, `ACCESS_DENIED`, and exact `Available: ...` balance strings. OWASP API1:2023 notes that object authorization should be enforced on every function using client-supplied object identifiers and that response differences materially lower the cost of enumeration and unauthorized intelligence gathering.
- **Evidence:** `MakeOfferOnBuilding` still exposes `COMPANY_NOT_FOUND` and returns precise available balance text when the buyer company lacks funds. `BuyFromExchange` and `SellToExchange` distinguish `ACCESS_DENIED`, `BANK_ACCOUNT_NOT_FOUND`, `BANK_ACCOUNT_MISMATCH`, and exact required or available balances. These are not equivalent to a generic object-authorization failure path.
- **Potential impact:** An authenticated competitor can use mutation probing to infer whether a company exists, whether a building is listed, whether a target account is linked to the company, and how close an opponent is to an affordability threshold.
- **Recommended fix:** Finish the response-normalization pass so foreign-object authorization failures collapse to `NOT_FOUND_OR_NOT_OWNED`, and move exact balance details to structured server-side logs rather than user-visible error payloads.
- **Status:** Open <!-- issue: #393 -->

### 2) Support ticket HTML preview relies on a regex-based sanitizer before rendering with `v-html`
- **Severity:** Medium
- **Affected project or surface:** `projects/MasterApi/Utilities/SupportTicketMarkdownProcessor.cs`, `projects/master-frontend/src/views/SupportAdminView.vue`, `projects/master-frontend/src/views/SupportTicketDetailView.vue`.
- **Risk description:** Support-ticket markdown is converted to HTML on the server and then sanitized by manually stripping a few patterns with regular expressions before the result is stored in `SanitizedPreviewHtml` and rendered with `v-html`. That approach removes some obvious vectors, but regex-based HTML sanitization is brittle and can miss malformed markup, nested HTML edge cases, namespace-specific attributes, and future browser parsing quirks. This is a browser-side trust boundary because the rendered preview is consumed by moderators and support users.
- **Evidence:** `SupportTicketMarkdownProcessor.SanitizeHtml` removes script-like tags, inline `on*` handlers, and `javascript:` in `href` or `src`, but it is not an allowlist DOM sanitizer. Both support views render `ticket.sanitizedPreviewHtml` directly with `v-html`. Existing support-ticket tests verify only basic script stripping and moderation gating, not a broader payload corpus.
- **Potential impact:** A crafted support ticket could bypass the current sanitizer and execute in a moderator or support user's browser, turning the support workflow into a stored-XSS path.
- **Recommended fix:** Replace the regex sanitizer with a maintained allowlist HTML sanitizer, keep unsafe-content detection separate from sanitization, and add regression tests with representative XSS payload families.
- **Status:** Open

### 3) MasterApi news trust-boundary hardening is live in code but lacks dedicated regression coverage
- **Severity:** Medium
- **Affected project or surface:** `projects/MasterApi/Types/Query.cs`, `projects/MasterApi/Types/Mutation.News.cs`, `projects/MasterApi.Tests`.
- **Risk description:** The code now correctly resolves draft-news access from trusted game-server credentials or authenticated privileged admin claims instead of caller-supplied requester email. That closes the direct trust-boundary flaw from earlier audits. However, the current test project does not contain explicit regression tests for `GetGameNewsFeed(includeDrafts)` or `UpsertGameNewsEntry`, which leaves a security-critical control vulnerable to silent future regressions.
- **Evidence:** `GetGameNewsFeed` now sets `includeDrafts` only when `TryResolveTrustedNewsServerIdentityAsync(...)` or `TryResolvePrivilegedNewsAdminIdentityAsync(...)` succeeds. `UpsertGameNewsEntry` rejects caller-supplied `RequesterEmail` and requires trusted server credentials or privileged admin identity. A targeted search across `projects/MasterApi.Tests` returned no explicit security tests for these operations.
- **Potential impact:** A later refactor could accidentally re-open anonymous draft reads or spoofed news writes without CI catching it.
- **Recommended fix:** Add focused integration tests for anonymous draft-read rejection, spoofed requester rejection, invalid server-key rejection, trusted server success, and privileged admin success.
- **Status:** Open

### 4) NPC bot runner still ships a committed shared default password
- **Severity:** Medium
- **Affected project or surface:** `projects/NPCBot/appsettings.json`, `projects/NPCBot/Configuration/BotOptions.cs`.
- **Risk description:** The NPC bot runner still ships with `BotPassword = "NpcBot!2025"` in both committed configuration and code defaults. The README documents this as a development placeholder and recommends overriding it in production, but the executable still starts with the placeholder if the operator forgets to override it. Because the password is shared across all bot accounts, one leaked or guessed credential weakens every bot account created by that runner.
- **Evidence:** `appsettings.json` sets `Enabled: true` and includes the placeholder password. `BotOptions.BotPassword` has the same default and does not enforce replacement at startup.
- **Potential impact:** A deployment that forgets to override the placeholder can expose predictable NPC bot credentials, enabling account takeover, impersonation, or bot-state manipulation.
- **Recommended fix:** Remove the committed password default, require a startup override or API-key mode outside local development, and fail fast when the placeholder is still configured.
- **Status:** Open

### 5) `projects/master-frontend` still carries a moderate production dependency advisory in `postcss`
- **Severity:** Medium
- **Affected project or surface:** `projects/master-frontend/package.json` and production dependency tree.
- **Risk description:** `npm audit --omit=dev` currently reports one moderate vulnerability: `postcss < 8.5.10` (`GHSA-qx2v-qp2m-jg93`, `CVE-2026-41305`). The advisory describes an XSS condition when user-submitted CSS is parsed and re-stringified into HTML `<style>` tags without escaping `</style>`. That exact pattern was not confirmed as reachable in this repo, so this is an operational dependency risk rather than an active exploit finding.
- **Evidence:** Local audit output for `projects/master-frontend` reports one moderate advisory and recommends `npm audit fix`. GitHub Advisory Database lists the patched version as `8.5.10`.
- **Potential impact:** If a future feature introduces CSS parsing or stringify flows with user-controlled CSS, the outdated dependency could become a reachable XSS primitive.
- **Recommended fix:** Upgrade `postcss` to `>= 8.5.10` and keep the frontend dependency-audit gate blocking unresolved production advisories.
- **Status:** Open

## Recommendations
1. Prioritize the support-preview sanitization replacement and the economy error-surface normalization, because both are still live trust boundaries rather than purely operational debt.
2. Add explicit integration coverage for the MasterApi news trust boundary so the current hardening cannot regress unnoticed.
3. Remove the NPC bot placeholder password and force operators to choose either API-key mode or an environment-provided secret.
4. Clear the remaining `postcss` advisory in `projects/master-frontend` and keep both frontends on a zero known production advisory baseline.
5. Keep the current strong controls in place: API-key scopes, deny-by-default middleware, trusted news identity resolution, server-side FX nonce and slippage validation, and token-boundary claim separation are all effective improvements that should remain part of the audit baseline.
