## Findings

### 1) OIDC `RequireHttpsMetadata=false` in Production-Base Configuration (Both APIs)

- **Severity:** Low (defense-in-depth; Authority is currently HTTPS)
- **Affected:** `projects/Api/appsettings.json` line 41, `projects/MasterApi/appsettings.json` line 92, `projects/MasterApi/Security/BiatecOidcOptions.cs` line 15, `projects/Api/Program.cs` line 324, `projects/MasterApi/Program.cs` line 306
- **Description:** The base `appsettings.json` of both APIs — the configuration layer that applies to every environment including Production unless overridden — sets `"RequireHttpsMetadata": false` for the `biatec-oidc` JWT bearer scheme. The game API's C# default (`BiatecOidcOptions.RequireHttpsMetadata = true`) is overridden by config; MasterApi's C# default is `false`, so even deleting the config key would not restore a secure default there. Neither `Program.cs` has a startup guard for this flag, unlike the existing guards for JWT signing keys, connection strings, and admin passwords.
- **Impact:** With `RequireHttpsMetadata=false`, the JWT bearer handler will accept a plain-HTTP OIDC discovery/metadata endpoint. The configured Authority (`https://google.biatec.io`) is HTTPS, so metadata retrieval is encrypted in practice; exploitation would require an attacker or operator to first change/override the Authority to an HTTP URL (e.g., via an environment variable on the deployment), at which point signing-key discovery could be intercepted and a forged-token trust chain established. The flag removes the framework's last-line protection against exactly that misconfiguration.
- **Recommendation:** Set `"RequireHttpsMetadata": true` in both base `appsettings.json` files and override to `false` only in `appsettings.Development.json`. Align `MasterApi/Security/BiatecOidcOptions.cs` to default `true` like the game API. Add a non-Development startup guard (matching the existing placeholder-secret guards) that fails fast when `BiatecOidc.Enabled` is true, `RequireHttpsMetadata` is false, or the Authority is not HTTPS, plus a startup regression test.
- **Status:** Open (carried as a residual note since 2026-05-30; formalized this audit)

### 2) .NET Runtime Patch Currency Depends on Push Cadence (CVE-2026-45591 Context)

- **Severity:** Low (currently patched; process gap)
- **Affected:** `projects/Api/Dockerfile`, `projects/MasterApi/Dockerfile` (base image `mcr.microsoft.com/dotnet/aspnet:10.0`), `.github/workflows/api-ci-cd.yml`, `.github/workflows/master-api-ci.yml`
- **Description:** Microsoft's June 2026 servicing release fixed CVE-2026-45591, an Important-rated unauthenticated denial-of-service (uncontrolled resource consumption) in ASP.NET Core, in runtime 10.0.9; the earlier out-of-band 10.0.7 release fixed CVE-2026-40372 in `Microsoft.AspNetCore.DataProtection`, which this stack uses for cookie sessions. The runtime patch level of the deployed containers is set by the floating `aspnet:10.0` base tag at image build time. Builds run on ephemeral GitHub-hosted runners (`ubuntu-latest`), which pull the base image fresh, and `api-ci-cd.yml` triggers on every push to `main` without path filters — so the 2026-06-20 push rebuilt and redeployed both APIs with runtime ≥10.0.9. Deployed services are therefore patched as of this audit.
- **Impact:** There is no time-based rebuild trigger. If `main` receives no pushes for weeks (it has been 17 days at audit time), future runtime security patches — including any follow-up DoS fixes relevant to a public-facing game API — do not ship. NuGet scanning (`dotnet list package --vulnerable`) does not cover the framework runtime, so this gap is invisible to the existing dependency audits.
- **Recommendation:** Add a `schedule:` (cron) trigger — weekly, or on the second Wednesday of each month after .NET patch Tuesday — to the API and frontend CI/CD workflows so images are rebuilt and redeployed even without code changes. Optionally log the runtime version at startup for deploy-time verification.
- **Status:** Open

### 3) esbuild 0.27.7 — Dev-Server Arbitrary File Read on Windows (GHSA-g7r4-m6w7-qqqr)

- **Severity:** Low (development tooling only)
- **Affected:** Both frontends — `esbuild@0.27.7` resolved solely via `vite@7.3.5` (devDependency); advisory range 0.27.3–0.28.0
- **Description:** esbuild's development server allows arbitrary file read on Windows. In this repository esbuild is reachable only through Vite's dev tooling; the production images serve static builds through nginx and contain no esbuild. `npm audit` lists the advisory even in `--omit=dev` output because of how the lockfile graph is evaluated, but the dependency path (`vite → esbuild`) is dev-only in both projects.
- **Impact:** A developer running `npm run dev` on Windows with the dev server exposed to a hostile network could have local files read. Same workstation-level risk class as the (now fixed) Vite advisories from the June audit.
- **Recommendation:** Clear at the next dependency cycle via `npm audit fix` (or a Vite point release that lifts esbuild past 0.28.0) in both frontend directories. Not release-blocking.
- **Status:** Open

### 4) nginx `add_header` Inheritance Drops Security Headers on Asset Responses (Both Frontends)

- **Severity:** Low
- **Affected:** `projects/frontend/nginx.conf`, `projects/master-frontend/nginx.conf`
- **Description:** nginx's `add_header` directives are inherited from the `http` block **only if** the current level defines no `add_header` of its own. Both configs declare the security headers (HSTS, CSP, `X-Content-Type-Options`, etc.) in the `http` block, but the static-asset location (`location ~* \.(js|css|png|...)$`) adds `Cache-Control`, the game frontend's `/sw.js` location adds `Cache-Control`, and `/health` adds `Content-Type`. Every response served from those locations therefore carries **none** of the security headers. The SPA document path (`location /`) declares no headers of its own, so `index.html` — where CSP and `X-Frame-Options` matter most — receives the full set. The practical losses on asset responses are `X-Content-Type-Options: nosniff` (MIME-confusion/CORB protection for scripts and styles) and `Strict-Transport-Security` (HSTS refresh on direct asset fetches).
- **Recommendation:** Move the security `add_header` set into a shared snippet (`include /etc/nginx/snippets/security-headers.conf;`) and include it in every location that declares its own `add_header`, or repeat the headers in those locations. Verify with `curl -I` against a `.js` asset in the container.
- **Status:** Open (pre-existing; first flagged this audit)

### 5) Game Frontend CSP/Header Hygiene: Missing `Permissions-Policy`, Stale Script Hash

- **Severity:** Informational
- **Affected:** `projects/frontend/nginx.conf` line 33
- **Description:** Two hygiene items on the game frontend's headers. (a) `Permissions-Policy` is not set — the master frontend sets `camera=(), microphone=(), geolocation=()` but the game frontend omits the header entirely; the previous risk-register wording incorrectly claimed it was set on both. (b) The CSP `script-src` still allowlists `'sha256-Rh8mWJSDr/iArX0d2PwoVaozUtvb51F4go7+NyfSvTc='`, the hash of the inline gtag bootstrap that commit `1f7018ad` moved into same-origin `/gtag-init.js` (now covered by `'self'`); the hash is dead weight and should be removed so the policy stays minimal. Related accepted trade-off worth recording: `connect-src 'self' https:` and `img-src 'self' data: https:` are broad (any HTTPS host) to accommodate Google Analytics regional endpoints, Sentry, and OpenStreetMap tiles; tightening to an explicit host list would reduce exfiltration surface if XSS ever landed, at the cost of maintenance.
- **Recommendation:** Add the same `Permissions-Policy` header used by the master frontend; delete the stale script hash from the CSP; optionally enumerate `connect-src` hosts (GraphQL API origins, `*.google-analytics.com`, `*.googletagmanager.com`, Sentry ingest, tile server) instead of `https:`.
- **Status:** Open
